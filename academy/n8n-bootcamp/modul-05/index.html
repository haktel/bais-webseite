MENTAL MODEL

Ein Workflow ist ein gerichteter Entscheidungsgraph

Linear ist nur der Anfang. Reale Prozesse verzweigen, wiederholen, stoppen, eskalieren und führen Daten später wieder zusammen.

Input→Validate→Decide→Route→Act→Join / Finish
Vertiefung öffnen

Kontrollfluss und Datenfluss gleichzeitig denken

Eine Branch-Entscheidung verändert nicht nur, welcher Node als nächstes läuft. Sie verändert auch, welche Daten später verfügbar sind, wie viele Items weiterlaufen und welche Seiteneffekte entstehen. Deshalb musst du jeden Pfad als Kombination aus Regel + Daten + Aktion + Fehlerpfad verstehen.

Kontrollfrage

Welcher Pfad wird gewählt?

Datenfrage

Welche Felder/Items existieren danach?

Realer Denkfehler: „Der IF ist nur eine Linie nach rechts.“ In Production kann TRUE eine Zahlung auslösen und FALSE einen manuellen Review. Das ist Geschäftslogik, kein Layout.

SWITCH

Mehrere klare Routes statt IF-Kaskade

Switch macht Regeln sichtbar

Drei oder vier explizite Ausgänge sind leichter zu verstehen als IF → FALSE → IF → FALSE → IF. Switch kann nach Regeln oder Expression routen.

05
FALLBACK

Unbekannte Werte dürfen nicht still verschwinden

Neue Region, neuer Ticket-Typ oder Tippfehler: Production braucht einen kontrollierten Default-Pfad.

DE → domestic EU → eu US → international OTHER → manual review
Vertiefung öffnen

Fallback ist eine Sicherheitsfunktion

Wenn morgen region="CH" ankommt und du nur DE/EU/US definiert hast, sollte das Item nicht unsichtbar verschwinden. Ein Fallback kann Manual Review, Error Queue oder Quarantine sein.

Bad Default

Alles Unbekannte automatisch als DE behandeln.

Good Default

Unbekannte Werte markieren, speichern und bewusst prüfen.

Change Management: Fallback-Metriken zeigen dir, wenn ein Quellsystem neue Werte eingeführt hat, bevor daraus stille Datenverluste werden.

07
DATA INTEGRITY

Falscher Merge ist ein Datenschutz- und Business-Risiko

Daten verschiedener Kunden falsch zu kombinieren ist schlimmer als ein sichtbarer Fehler.

CRM orderId=O-7 ─┐ ├→ Merge by orderId → korrekt ERP orderId=O-7 ──┘
Vertiefung öffnen

Identity before Merge

Bevor zwei Pfade zusammengeführt werden, muss klar sein, welcher Schlüssel die fachliche Identität beschreibt: customerId, orderId, ticketId. Namen oder Listenposition sind oft ungeeignet.

Incident-Beispiel: Zwei Arrays haben gleiche Länge, aber unterschiedliche Sortierung. Merge by Position verbindet Mina mit Jonas’ Rechnungsdaten. Der Workflow läuft grün – die Daten sind trotzdem falsch.
Test

Absichtlich unterschiedliche Reihenfolgen verwenden und prüfen, ob der Join trotzdem korrekt bleibt.

LOOP OVER ITEMS

Viele Items kontrolliert nacheinander oder in Batches verarbeiten

Loop Over Items teilt die Eingabemenge in Batches und führt denselben Verarbeitungspfad wiederholt aus.

100 Items
→
Batch 10
↻
10 Durchläufe
Vertiefung öffnen

Zwei Outputs mental verstehen

Loop Output läuft pro Batch. Der Verarbeitungspfad führt zurück zum Loop Node. Done Output wird erst ausgelöst, wenn alle Batches abgearbeitet sind.

Loop Over Items→ each batch →Process↺ zurückDone→Aggregate / Report
Typischer Fehler

Der Rückweg zum Loop fehlt. Ergebnis: nur der erste Batch wird verarbeitet.

BATCHING

Batch Size ist eine Betriebsentscheidung

Batch-Größe beeinflusst Throughput, Rate Limits, Memory, API-Kosten und Fehlerauswirkung.

Batch 1maximale Kontrolle, langsam
Batch 10ausgewogener Durchsatz
Batch 1000hohe Last / Blast Radius
Vertiefung öffnen

Downstream bestimmt dein Tempo

Wenn eine API 60 Requests pro Minute erlaubt, darf dein Workflow nicht 1.000 Items gleichzeitig feuern. Batching, Wait und Retry-Strategien passen den Datenfluss an die Kapazität des Zielsystems an.

LOOP SAFETY

Schleifen, Retries und Idempotency

Wiederholung ist gefährlich, wenn die Aktion einen Seiteneffekt hat: Zahlung, Order, E-Mail oder Datenbank-Insert.

Item O-1001 → POST order → Timeout → Retry → ??? zweite Order?
Vertiefung öffnen

Idempotency schützt vor Doppelaktionen

Wenn derselbe fachliche Request erneut ausgeführt wird, sollte er nicht unbeabsichtigt einen zweiten Seiteneffekt erzeugen. Dafür können Idempotency Keys, eindeutige Business IDs oder Dedupe-Tabellen verwendet werden.

AktionRetry-RisikoSchutz
GET Customerniedrignormaler Retry
POST PaymenthochIdempotency Key
Send Emailmittel/hochmessageId / sent-log
DB INSERThochunique key / upsert
Infinite Loop

Jede Schleife braucht eine erreichbare Terminierung. Counters, max pages, max retries und Timeouts sind technische Sicherheitsgrenzen.
