MODUL 05 · PRAXISWERKSTATT

Flow Control, Merge & Loops mit Business-Regeln

Routing ist Business-Logik. Du musst Grenzwerte, Fallbacks, Batch-Grenzen, Merge-Schlüssel und wiederholbare Side Effects kontrollieren.

DECIDEIF · Switch
ITERATELoop · Batch
RECONCILEMerge · Keys
REPEAT SAFELYIdempotency
Regel: Jede Branch-Regel braucht Grenzwerttests und einen definierten Fallback.
FALL 01

Lead Routing · Budget + Thema

Ein typischer Vertriebsprozess routet Anfragen nach Budget, Thema und Datenqualität.

Quelle: n8n IF →
Lead
→
Valid?
→
Budget ≥ 5000?
→
Qualified / Standard
→
CRM

Deine Aufgabe

  1. Teste 4999, 5000, 5001.
  2. Was passiert bei null/"5000"?
  3. Welche Regel hat Priorität: invalid email oder high budget?
  4. Fallback?

Break/Fix

String "7500" wird falsch verglichen. Normalisierung vor Routing einbauen.

Musterlösung öffnen

Erst validate/normalize, sonra business routing. Invalid data never bypasses validation because of high budget.

FALL 02

Stepstone · große Mengen kontrolliert batchen

Stepstone beschreibt Millionen jobbezogener Dokumente pro Monat; Loop/Batch-Entscheidungen werden bei dieser Größenordnung operativ relevant.

Quelle →
10kItems
100Batch Size
100Batches
boundedConcurrency

Deine Aufgabe

  1. Batch size 100 ise kaç batch?
  2. Batch 37 fail olursa?
  3. Cursor ne zaman ilerler?
  4. API rate limit nasıl korunur?

Break/Fix

Loop yanlış bağlandı ve done output yerine tekrar loop'a dönüyor. Sonsuz döngüyü tespit et.

Musterlösung öffnen

Loop termination explicit. Batch checkpoint yalnız successful unit sonrası. Failed batch retry/review; completed batches yeniden side effect yaratmamalı.

FALL 03

Merge · pozisyona göre değil Domain Key'e göre

İki kaynağın item sırası farklı olabilir. Merge kararı stabil bir domain key ile yapılmalıdır.

Quelle: n8n Merge →
CRM: C1,C2,C3
ERP: C3,C1,C2
Key
customerId
↓
Merge by customerId
↓

Deine Aufgabe

  1. Position merge neden tehlikeli?
  2. Duplicate key varsa?
  3. Missing key?
  4. Inner vs left-style behavior?

Break/Fix

CRM ve ERP farklı sırada. Yanlış müşterinin faturası yanlış CRM kaydına bağlandı. Root cause ve prevention yaz.

Musterlösung öffnen

Stable domain key + uniqueness validation. Duplicate/missing key route to exception instead of silent merge.

FALL 04

Idempotency · aynı event ikinci kez zarar vermesin

Network retry veya webhook replay aynı business event'i tekrar çalıştırabilir.

Quelle: n8n Looping Concepts →
eventId
→
seen?
→ no →
Side Effect

mark seen

Deine Aufgabe

  1. Mail/CRM update hangi key ile dedupe?
  2. Key ne kadar tutulur?
  3. Side effect başarılı ama mark-seen fail olursa?
  4. Transaction/outbox pattern nasıl yardımcı olur?

Break/Fix

Aynı invoice event iki kez geldi ve iki mail gönderildi. Idempotency boundary'yi düzelt.

Musterlösung öffnen

Persistent domain/event key before side effect or transactional pattern. "Workflow bir kez çalıştı" değil, "business effect bir kez gerçekleşti" hedeflenir.

FALL 05 · CAPSTONE

Order Fulfillment Routing

Orders EU/non-EU, stok durumu, fraud score ve priority'ye göre farklı yollar izliyor.

Order
→
Validate
→
Switch Region
→
Stock/Fraud
→
Fulfill / Review

Pflichtaufgabe

  1. Switch outputs + fallback tanımla.
  2. Fraud ≥ 0.8 → review.
  3. Stock items loop/batch.
  4. Inventory + CRM results merge by orderId.
  5. Duplicate order event idempotent olsun.
  6. 8 boundary tests yaz.

Ready to Teach

Bir flowchart üzerinde IF, Switch, Loop ve Merge'in farklı sorumluluklarını anlat.

Referenzlösung öffnen

Validation → region switch → fraud/stock branches → batched item operations → merge by orderId → idempotent fulfillment key → audit.
