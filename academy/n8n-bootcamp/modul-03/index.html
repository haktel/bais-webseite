01
HTTP MENTAL MODEL

Request rein – Response zurück

HTTP ist ein Request/Response-Protokoll. Ein Client stellt eine konkrete Anfrage; ein Server antwortet mit Status, Headers und optional Daten.

Client / n8n→ REQUEST →API Server→ RESPONSE →n8n
Vertiefung öffnen

Ein API-Call ist immer ein Vertrag

Der Client sagt: was er will (Methode), wo (URL), unter welchen Bedingungen (Headers) und gegebenenfalls mit welchen Daten (Body). Der Server antwortet mit einem Statuscode, Response-Headers und häufig JSON.

REQUEST
GET /customers/C-1042 HTTP/1.1
Host: api.example.com
Accept: application/json
RESPONSE
200 OK
Content-Type: application/json

{"id":"C-1042","name":"Mina"}
Transport

HTTPS schützt die Verbindung per TLS. Es sagt aber nicht automatisch, ob dein Request fachlich erlaubt oder dein Token ausreichend berechtigt ist.

Debugging

Trenne Netzwerkfehler, Authentifizierung, Validierung und serverseitige Fehler anhand von Status und Response.

REALER FALL · DELIVERY HERO

Wie dieses Prinzip in Production sichtbar wird

Delivery Hero automatisierte einen Account-Recovery-Prozess mit einem n8n Workflow. Nach der Freigabe durch den direkten Manager ruft n8n Okta-, Jira- und Google-Systeme per API auf. Bei rund 800 Recovery-Anfragen pro Monat sank die durchschnittliche Sperrzeit von 35 auf 20 Minuten; laut Case Study wurden dadurch etwa 200 Stunden pro Monat eingespart.

Übertrag auf diesen Lernpunkt

HTTP ist der Transportvertrag zwischen Systemen: Request rein, Status/Headers/Body zurück. Der Workflow muss beide Richtungen bewusst modellieren.

02
REST

Resources statt „irgendwelche URLs“

REST-orientierte APIs modellieren fachliche Ressourcen wie Customers, Orders oder Tickets und verwenden HTTP-Methoden für Operationen.

/customers /customers/C-1042 /customers/C-1042/orders /orders/ORD-88
Vertiefung öffnen

Resource und Representation unterscheiden

Die Resource ist das fachliche Objekt, z. B. Kunde C-1042. JSON ist nur eine mögliche Darstellung dieser Resource. Das hilft beim API-Design und beim Lesen fremder APIs.

Collection/customers
→
Single Resource/customers/C-1042
→
Subresource/customers/C-1042/orders
Praxisfrage

Wenn du alle offenen Tickets eines Kunden brauchst: Ist /customers/C-1042/tickets?status=open verständlicher als /doTicketSearch?cust=C-1042&s=1? Gute APIs reduzieren Interpretationsaufwand.

GET, POST, PUT, PATCH, DELETE

Die Methode beschreibt die Absicht des Requests. Falsche Methode kann zu 405, unerwarteter Business-Logik oder gefährlichen Seiteneffekten führen.

POSTerstellen / starten
PUTersetzen
PATCHteilweise ändern
DELETElöschen

GETlesenGET /orders/88sollte keinen fachlichen Zustand ändern
POSTerstellen / Aktion startenPOST /orderskann neue Resource erzeugen

06
BODY & SCHEMA

JSON senden, aber mit Vertrag

POST, PUT und PATCH senden häufig strukturierte Daten im Body. Production braucht Schema, Pflichtfelder, Datentypen und Validierungsregeln.

Request Body
{
 "customerId":"C-2048",
 "name":"Mina Yilmaz",
 "email":"mina@example.com"
}
Validierung
customerId: required string
name: required string
email: valid email
Vertiefung öffnen

Ein lesbares JSON ist noch kein gültiger Business Request

{"email":"abc"} ist syntaktisch gültiges JSON, aber fachlich möglicherweise ungültig. Deshalb trennt man Parsing von Schema-/Business-Validierung.

Raw Body→JSON Parse→Schema Validation→Business Logic
422 statt stiller Fehler

Ein kontrollierter 4xx-Response ist besser als Daten ungeprüft zu speichern und später inkonsistente Systeme zu reparieren.

WEBHOOKS

Push statt dauernd nachfragen

Webhook: Quellsystem meldet ein Ereignis aktiv. Polling: dein Workflow fragt regelmäßig nach, ob sich etwas geändert hat.

WEBHOOK · PUSHEvent passiert → System sendet sofort HTTP Request → Workflow startet.
POLLING · PULLSchedule → API GET → „Gibt es Neues?“ → wiederholen.
Vertiefung öffnen
Webhook gut

Wenn Provider Events zuverlässig pushen kann: Zahlung, GitHub Event, Formular, CRM Callback.

Polling nötig

Wenn Provider keine Webhooks bietet oder periodischer Abgleich bewusst gewünscht ist.

Lab-Auftrag & Break/Fix öffnen

A · GET verstehen

  1. Starte GET und identifiziere Methode, Base URL, Query Parameters und Headers.
  2. Vergleiche gesendete Query-Werte mit dem Echo des externen Servers.
  3. Erkläre, warum GET hier keinen JSON Body braucht.

B · POST verstehen

  1. Starte POST und unterscheide Headers von JSON Body.
  2. Prüfe, ob externe API die gesendeten JSON-Werte zurückspiegelt.
  3. Erkläre, warum Content-Type: application/json relevant ist.

C · BREAK IT

  1. Entferne Customer ID.
  2. Verwende beim POST eine ungültige E-Mail.
  3. Erkläre, warum der Workflow vor dem externen HTTP Request mit 422 stoppen soll.

D · DEBUG IT

  1. Stelle dir HTTP 401 vor: Welche Schicht prüfst du?
  2. HTTP 429: Welche Retry-Strategie wäre korrekt?
  3. HTTP 500: Wann retry, wann abbrechen?
  4. Zeichne aus dem Kopf Request → Response inklusive Methode, URL, Header, Body, Status.
