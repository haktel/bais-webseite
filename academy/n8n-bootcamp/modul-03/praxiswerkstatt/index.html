MODUL 03 · PRAXISWERKSTATT

REST APIs & Webhooks unter realen Betriebsbedingungen

Hier zählt nicht nur ein HTTP 200. Du musst Requests lesen, Statuscodes richtig interpretieren, Signatures prüfen, Pagination vollständig abarbeiten und Rate Limits kontrolliert behandeln.

REQUESTMethod · URL · Header · Body

RECOVER4xx · 5xx · Retry
Regel: Vor jedem HTTP Node musst du Method, Endpoint, Auth, Request Body, erwartete Statuscodes und Retry-Regel erklären können.
FALL 01

GitHub · Webhook Delivery validieren

GitHub dokumentiert Webhook-Signatures, damit Empfänger prüfen können, ob eine Delivery authentisch und unverändert ist.

Quelle: GitHub Docs →
GitHub
→

→

→

Process

Deine Aufgabe

  1. Welche Header/Body-Daten brauchst du?
  2. Warum raw body?
  3. Was passiert bei falscher Signature?
  4. Welche Daten dürfen erst nach Verification verarbeitet werden?

Break/Fix

Body wird vor Verification JSON-geparst und neu serialisiert. Signature passt nicht mehr. Erkläre warum.

Musterlösung öffnen

Verification auf genau dem Payload durchführen, das der Provider signiert hat. Mismatch → 401/403 bzw. reject; keine Business Action.

  1. Signature valid ama event aynıysa ne olur?
  2. eventId nerede persist edilir?
  3. Timeout sonrası provider tekrar gönderirse?
  4. Payment side effect nasıl exactly-once'e yaklaşır?

Break/Fix

Aynı başarılı ödeme eventi üç kez gelir. CRM ve mail sadece bir kez çalışmalı.

Musterlösung öffnen

Signature sadece authenticity sağlar; replay ayrı problemdir. Persistent eventId/idempotency key ile ikinci ve üçüncü delivery no-op olur.

FALL 03

REST Statuscodes · 400, 401, 403, 404, 409, 422, 429, 5xx

HTTP status code yalnız UI mesajı değil; retry ve recovery kararını belirler.

Quelle: MDN HTTP Status →
4xxclient/request problem
429rate limit
5xxserver/transient
2xxsuccess class

Entscheide

  1. 400 → retry?
  2. 401 → credential refresh/check?
  3. 403 → scope/permission?
  4. 429 → backoff?
  5. 503 → bounded retry?

Break/Fix

Workflow retries 422 zehn kez. Neden yanlış? Hangi durumda veri düzeltilmeden retry anlamsızdır?

Musterlösung öffnen

4xx çoğunlukla request/auth/permission düzeltmesi ister. 429 ve bazı 5xx bounded retry/backoff adaylarıdır. Retry policy status code + idempotency ile birlikte tasarlanır.

Pagination · ilk sayfa başarı değildir

Deine Aufgabe

  1. Cursor vs page-number farkı?
  2. Stop condition?
  3. Duplicate page nasıl engellenir?
  4. 10.000 kayıt memory'e tek seferde alınmalı mı?

Break/Fix

Workflow yalnız ilk 100 kaydı getiriyor ve „success“ diyor. Gerçek completeness check tasarla.

Musterlösung öffnen

Pagination metadata/Link/cursor izlenir; next yoksa biter. Büyük dataset batch/process edilir; expected count veya terminal cursor ile completeness doğrulanır.

FALL 05 · CAPSTONE

Kunden-API: Lead Sync mit Rate Limit

Bir SaaS API dakikada 60 request kabul ediyor. Her gece 2.400 lead sync edilecek.

CRM Source
Normalize
Batch
HTTP API
↓

Pflichtaufgabe

  1. Batch size ve delay belirle.
  2. 429 için bounded backoff kur.
  3. 400/422 için dead-letter/review path.
  4. Cursor/checkpoint yalnız başarılı batch sonrası güncellensin.
  5. 5 acceptance tests yaz.

Ready to Teach

Neden „HTTP Request Node grün“ demek veri sync tamamlandı demek değildir?

Referenzlösung öffnen

Rate-aware batching + Retry-After/backoff. Validation errors ayrı kuyruğa. Checkpoint commit yalnız batch başarıyla tamamlandıktan sonra. Metrics: processed, failed, retried, rate-limited, remaining.
