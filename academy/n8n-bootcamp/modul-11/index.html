INTEGRITY & REPLAY

Hash, HMAC und das Problem wiederholter Requests

Integrity Verification erkennt Veränderungen; Replay Protection verhindert, dass derselbe gültige Request erneut verarbeitet wird.

eventId + timestamp + body→verify signature→fresh?→eventId seen?→process once
Vertiefung öffnen

SHA-256 ≠ HMAC

SHA-256 allein liefert keine schlüsselbasierte Authentizität. HMAC-SHA256 verwendet einen geheimen Schlüssel. Das Academy Live Lab zeigt einen echten SHA-256-Integrity-Mismatch; in produktiven Webhooks wird für Authentizität HMAC bzw. die Provider-Signature verwendet, während das Secret im Credential Store bleibt.

Integrity

Expected vs computed digest.

Replay

Timestamp tolerance + eventId persistent dedupe.

Reales Szenario: Ein Provider sendet ein gültig signiertes Event nach einem Network Timeout erneut. Obwohl die Signature weiterhin gültig ist, muss ein zweiter Business Side Effect durch Idempotency bzw. Dedupe verhindert werden.

Übertrag

Hash zeigt Datenänderung; HMAC/provider signature verbindet Integrity mit Secret Material. Replay bleibt eine separate Kontrolle.

Allowlist, DNS und Redirect-Kette

Validiere Protokoll und Host. Blockiere private, Loopback- und Link-Local-Bereiche. Prüfe auch das Ziel nach Redirects erneut. Wenn möglich, wählt der Benutzer eine freigegebene Destination-ID statt eine beliebige URL einzugeben.

SECURE LOGGING

Logs sollen nützlich sein – kein Data Dump

Observability braucht Kontext, aber keine Secrets und keine unnötigen personenbezogenen Daten.

Unsafe Log
{"email":"mina@example.com",
 "token":"tok_prod_...",
 "password":"..."}
Operational Log
{"requestId":"req-42",
 "customer":"m***@example.com",
 "route":"support",
 "status":"success"}
Vertiefung öffnen

Correlation without disclosure

requestId bzw. correlationId schaffen eine gemeinsame Trace-Spur über Parent, Child und externe API-Aufrufe. Statt Token, Raw-Auth-Header oder vollständige Kundendatensätze zu loggen, werden bereinigte Metadaten verwendet.

DATENSCHUTZ & RETENTION

„Speichern können“ bedeutet nicht automatisch „speichern dürfen oder müssen“

Für personenbezogene Daten gehören Purpose, Minimization, Access, Retention und Deletion zum technischen Design.

Purposewarum wird verarbeitet?
Retentionwie lange?
Deletionaus welchen Systemen?
Vertiefung öffnen

Ohne Data Map wird Deletion unzuverlässig

Kundendaten können im CRM, in Data Tables, Execution Logs, Object Storage und externen SaaS-Systemen liegen. Ein Retention-/Deletion-Prozess muss diese Kopien kennen. Rechtsgrundlage und konkrete Fristen werden für den jeweiligen Use Case gesondert festgelegt.

Important

Encryption ist ein wichtiger technischer Control, ersetzt aber weder Purpose Limitation noch Minimization, Access Control oder Retention-Regeln.

A · Trusted

  1. Expected und computed SHA-256 müssen übereinstimmen.
  2. HTTPS public target allow.
  3. Action safe; final allow.

B · Tampered

  1. Expected digest eski/intended body'ye ait.
  2. Da der Amount verändert wurde, unterscheidet sich der computed Digest.
  3. Fail closed: action block.

C · PII / Secret

  1. Die Business-Daten enthalten E-Mail, Telefon und Token.
  2. Das Audit Log muss den Token vollständig redigieren und E-Mail/Telefon maskieren.
  3. Erkläre den Unterschied zwischen Processing Need und Logging Need.

D · SSRF

  1. Target link-local metadata address.
  2. Network policy block.
  3. Bewerte das Risiko von Redirect- und Private-DNS-Bypässen.

E · Destructive

  1. delete_user high impact.
  2. Human approval required.
  3. Es darf kein autonomer Side Effect ausgeführt werden.

F · DESIGN IT

  1. Entwirf für einen realen Payment-Webhook HMAC, Timestamp-Prüfung und eventId-Dedupe.
  2. Secret nerede tutulacak?
  3. Welche Logs werden aufbewahrt?
