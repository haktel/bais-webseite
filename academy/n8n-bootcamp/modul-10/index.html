01
MODULARITY

Copy-Paste-Divergenz stoppen

Wenn derselbe Normalisierungscode in zwölf Workflows kopiert wurde, existieren zwölf Wartungspunkte.

Copy-Paste

Normalize Lead v1, v1.1, v1.3 … unterschiedliche Verhaltensweisen.

Reusable Component

Ein Normalize-Lead-Contract; alle Caller verwenden dieselbe Logik.

Vertiefung öffnen

Reuse bedeutet mehr als weniger Nodes

Der eigentliche Gewinn sind ein Contract, ein Testsatz, ein Owner, ein zentraler Bugfix und kontrolliertes Change Management. Triviale einmalige Logik zwanghaft in einen Sub-Workflow auszulagern wäre dagegen Over-Engineering.

Extraction Rule

Logik ist ein guter Component-Kandidat, wenn sie wiederkehrt, unabhängig testbar ist und eine klare Input-/Output-Grenze besitzt.

03
INPUT CONTRACT

Der Child muss nicht alle Parent-Daten akzeptieren

Das Workflow Input Schema definiert Feldnamen und Datentypen; das Parent-Mapping übergibt nur die tatsächlich benötigten Daten.

Parent DataleadId,email,source,internalSecret,adminFlag
→ CONTRACT →
Child InputsleadId,email,source
Vertiefung öffnen

Der Contract ist zugleich eine Data-Minimization-Grenze

Wenn der Child für die Normalisierung internalSecret nicht benötigt, wird dieses Feld nicht übergeben. Das reduziert sowohl Kopplung als auch das Risiko unnötiger Datenweitergabe.

Type Contract

Wenn ein String erwartet wird, aber ein Object eintrifft, soll der Fehler an der Contract-Grenze sichtbar werden und nicht später als versteckter TypeError.

04
OUTPUT / ERROR CONTRACT

Success- und Failure-Shape müssen gleichermaßen stabil sein

Der Output einer Component muss für Caller eindeutig parsebar, dokumentiert und versionierbar sein.

Stable Success
{"valid":true,
 "contractVersion":"1.0",
 "lead":{...}}
Stable Validation
{"valid":false,
 "errors":["email_invalid"],
 "lead":{...}}
Vertiefung öffnen

Business Error und System Error trennen

Eine ungültige E-Mail kann ein erwarteter Business-Validation-Fall sein; eine nicht erreichbare Datenbank ist dagegen ein Systemfehler. Der Caller muss beide unterschiedlich behandeln.

Contract Test

valid immer Boolean? errors her zaman array mi? contractVersion mevcut mu?

05
SYNC / ASYNC

Parent sonucu bekleyecek mi?

Wait for Sub-Workflow Completion ist eine echte Architekturentscheidung.

SynchronousDer Parent benötigt den Child-Output; wait=true.
AsynchronousFire-and-forget; separates Monitoring und Correlation sind erforderlich.
Vertiefung öffnen

Asynchronität reduziert Kopplung, erhöht aber die Betriebsanforderungen

Wenn der Child nach einer bereits gesendeten 202/Accepted-Antwort fehlschlägt, ist der Fehler nicht mehr über die ursprüngliche Parent-Response sichtbar. Dafür braucht es Error Workflow, Correlation ID und einen Status Store.

Use Case

Lead-Normalisierung kann synchron laufen; lange PDF-Verarbeitung oder Bulk-Notifications können asynchron ausgeführt werden.

06
ITEM MODE

Alle Items in einer Execution oder eine Execution pro Item?

In modernem n8n ist in vielen Fällen Loop Over Items plus Sub-Workflow run once mit explizitem Batching klarer nachvollziehbar.

All Items100 item → 1 child execution
Loop Batch 10100 Items → 10 kontrollierte Aufrufe
Per Itemhoher Overhead / höherer Observability-Bedarf
Vertiefung öffnen

Auswirkungen der Granularität

Execution-Anzahl, Failure Isolation, Transaction Boundary, Rate Limits und Logs hängen von der Item-Granularität ab. In möglichst kleine Einheiten zu zerlegen ist nicht automatisch die beste Lösung.

COMPONENT BOUNDARY

Eine Component sollte einen klaren Reason-to-Change besitzen

Normalisierung, CRM, E-Mail, Invoice, AI und Datenbank in einen einzigen Child zu packen ist keine Modularität.

Normalize Leaddata contract
Send Notificationmessage delivery
CRM UpsertCRM mapping
Audit Eventtraceability
Vertiefung öffnen

High cohesion, low coupling

Nodes innerhalb einer Component sollten zur gleichen Verantwortung gehören und gemeinsam geändert werden. Components kommunizieren über Contracts und dürfen nicht von internen Node-Namen anderer Children abhängen.

WORKFLOW-AS-CODE

Git → Test → Deploy → Smoke

BAIS deployt die echten n8n-Workflow-JSONs per API aus GitHub in die RepoCloud-n8n-Instanz.

Branch→PR→Platform Tests→Merge→n8n API Deploy→Smoke Test
Vertiefung öffnen

Source-controlled sub-workflow reference

Mit Modul 10 wurde auch die Deploy-Pipeline erweitert: Der Parent referenziert den wiederverwendbaren Child-Workflow im Source-JSON per Name; die GitHub Action löst beim Deployment die reale n8n-Workflow-ID auf und trägt sie in den Parent ein. Manuelles Kopieren der ID entfällt.

Secrets

Workflow-JSON wird versioniert; Secret Values werden nicht versioniert. Credential-Referenzen und GitHub Repository Secrets werden erst zur Laufzeit genutzt.

PRODUCTION ARCHITECTURE

Dependency Graph kontrollieren

Mit wachsender Zahl wiederverwendbarer Components wird Governance auf Plattformebene erforderlich.

COMPONENT CATALOG · OWNERS
TYPED CONTRACTS · VERSIONS
DEPENDENCY GRAPH · CALLERS
TESTS · DEPLOY · ROLLBACK

Vertiefung öffnen

Shared component blast radius

Wenn 20 Workflows denselben Child verwenden, kann ein Incident in dieser Component 20 Prozesse betreffen. Error Rate, Duration, Caller-/Version-Metadaten und Rollback-Plan werden dadurch kritisch.

Circular Dependency: Sub-Workflow-Ketten wie A → B → A können rekursive Executions erzeugen. Der Dependency Graph sollte azyklisch oder explizit begrenzt sein.

A · Standard

  1. Der Parent ruft den Child auf.
  2. Prüfe contractVersion=1.0 und valid=true.

B · Messy

  1. E-Mail und Whitespace werden im Child normalisiert.
  2. Warum sollte diese Logik nicht in den Parent kopiert werden?

C · Extra Fields

  1. Der Parent enthält internalSecret/adminFlag.
  2. Das deklarierte Input-Mapping darf diese Felder nicht über die Child-Grenze weitergeben.
  3. Erkläre die Data Minimization.

D · Invalid

  1. Child crash yerine stable validation contract döndürür.
  2. Wie soll der Parent diesen Fall routen?

E · DESIGN IT

  1. Entwirf ein Input-/Output-Schema für eine Notification-Component.
  2. Entwirf einen Migrationsplan, falls v2 einen Breaking Change benötigt.
