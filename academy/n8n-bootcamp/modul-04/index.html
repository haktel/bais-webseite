01
AUTHN / AUTHZ

Wer bist du – und was darfst du?

Authentication und Authorization sind zwei getrennte Entscheidungen. Wer sie vermischt, debuggt 401 und 403 falsch und vergibt oft zu viele Rechte.

Authentication„Wer oder was bist du?“ Credential prüfen.
→
Authorization„Welche Resource/Action darfst du?“ Scope/Role/Policy prüfen.
Vertiefung öffnen

Zwei Entscheidungen, zwei Fehlerklassen

Ein gültiger Token kann eine Identität erfolgreich authentisieren und trotzdem für eine bestimmte Resource nicht autorisiert sein. Deshalb kann derselbe Client bei Endpoint A 200 und bei Endpoint B 403 bekommen.

401Identität nicht erfolgreich authentisiert: Credential fehlt, falsch oder abgelaufen.
403Identität bekannt, aber Scope, Rolle oder Policy erlaubt die Operation nicht.
Credential→Identity→Scopes / Roles→Protected Resource
Praxis

Wenn du einen 403-Fehler mit „neuen Token erzeugen“ bekämpfst, obwohl dem Token nur ein Scope fehlt, behebst du nicht die Ursache.

BEARER TOKEN

Wer das Token besitzt, kann es verwenden

Bearer Tokens werden typischerweise im Authorization Header übertragen und sind oft zeitlich begrenzt und scopegebunden.

Authorization: Bearer eyJ... └── niemals loggen ──┘
Vertiefung öffnen

Bearer bedeutet Besitznachweis

Bei einem klassischen Bearer Token gibt es keinen zusätzlichen Besitzbeweis pro Request. Wird das Token gestohlen, kann der Angreifer es bis Ablauf oder Widerruf verwenden. Deshalb sind kurze Laufzeiten, TLS, sichere Speicherung und minimale Scopes wichtig.

04
BASIC AUTH

Einfaches Username/Passwort-Schema

HTTP Basic Auth überträgt Benutzername und Passwort Base64-kodiert im Authorization Header. Base64 ist keine Verschlüsselung.

academy:demo-only ↓ Base64 Authorization: Basic YWNhZGVteTpkZW1vLW9ubHk=
Vertiefung öffnen

TLS ist Pflicht

Base64 kann problemlos dekodiert werden. Vertraulichkeit entsteht nur durch HTTPS/TLS. Basic Auth ist für manche interne oder Legacy-APIs weiterhin real, sollte aber mit dediziertem Service Account, begrenzten Rechten und sicherer Credential-Speicherung eingesetzt werden.

Username + Password→Base64 Encoding→Authorization Header→HTTPS API
Falsch

„Base64 sieht unlesbar aus, also ist das Passwort verschlüsselt.“

Richtig

Base64 ist Encoding. Schutz kommt von TLS und Secret-Management.

LEAST PRIVILEGE

Nur die Rechte, die wirklich gebraucht werden

Scopes und Rollen begrenzen, welche Ressourcen und Aktionen ein Credential ausführen darf.

ScopeLead ReaderLead WriterAdmin
customer:read✓✓✓
customer:write—✓✓
user:delete——✓
Vertiefung öffnen

„Alle Scopes“ ist kein Komfort, sondern Risiko

Wenn ein Workflow nur Kontakte lesen muss, braucht er keine Rechte zum Löschen von Benutzern oder Ändern von Billing-Daten. Least Privilege reduziert den möglichen Schaden bei Leak, Bug oder falsch gebauter Automation.

07
OAUTH2

Delegierter Zugriff ohne Passwortweitergabe

OAuth2 erlaubt einer Anwendung Zugriff auf Ressourcen, ohne dass der Benutzer sein Passwort direkt an diese Anwendung weitergibt.

User
→
Client App
→
Authorization Server
→
Access Token
→
Resource API
Vertiefung öffnen

Vier Rollen mental trennen

Resource Owner ist häufig der User. Client ist die Anwendung/n8n-Integration. Authorization Server authentisiert und stellt Tokens aus. Resource Server ist die eigentliche API.

Reales Beispiel: Google Calendar

  1. Du klickst „Google verbinden“.
  2. Google zeigt Consent: welche Calendar-Berechtigungen werden angefordert?
  3. Nach Zustimmung erhält die Anwendung einen Authorization Code.
  4. Der Code wird serverseitig gegen Access/Refresh Token getauscht.
  5. Der Workflow ruft Calendar API mit Access Token auf.
Kein Passwort-Sharing

Dein n8n Workflow braucht nicht das Google-Passwort des Users. Er arbeitet mit begrenzten, widerrufbaren Tokens.

Redirect URI ist Teil der Vertrauensbeziehung

Der Provider akzeptiert nur registrierte Redirect URIs. So soll verhindert werden, dass Authorization Codes an beliebige Ziele geschickt werden. Zusätzlich wird heute bei vielen Public Clients PKCE verwendet, um Code-Interception zu erschweren.

Refresh Token ist oft wertvoller als Access Token

Ein Access Token läuft vielleicht nach Minuten oder einer Stunde ab. Ein Refresh Token kann deutlich länger gültig sein und wiederholt neue Access Tokens erzeugen. Deshalb gehört es besonders streng geschützt und bei Logout/Widerruf entsprechend behandelt.

SECRET STORAGE & ROTATION

Secrets haben einen Lebenszyklus

Ein Credential wird erstellt, verteilt, genutzt, überwacht, rotiert und irgendwann widerrufen. „Einmal Key erzeugt“ reicht nicht.

Rotation ohne Ausfall planen

Viele Systeme erlauben kurzzeitig zwei gültige Keys. Dann erzeugst du Key B, rollst ihn aus, testest, widerrufst Key A und prüfst Logs. Bei einem Leak wird Rotation nicht irgendwann, sondern sofort durchgeführt.

Credential Leak: Ein API Key landet versehentlich in Git, Screenshot, Ticket oder Chat. Nur den Text zu löschen reicht nicht. Das Secret gilt als kompromittiert → widerrufen/rotieren → Zugriffe auditieren → Ursache beheben.

PRODUCTION LIFECYCLE

Service Accounts, Ownership und Audit

Ein produktiver Workflow sollte nicht am persönlichen Token eines Mitarbeiters hängen. Credentials brauchen technische und organisatorische Eigentümer.

Service Account ├─ Zweck: CRM Lead Sync ├─ Scope: customer:read/write ├─ Owner: Automation Team ├─ Env: Production ├─ Rotation: 90d / on incident └─ Workflows: Lead-01, CRM-02
Vertiefung öffnen

Personen verlassen Firmen – Workflows sollen weiterlaufen

Persönliche Tokens brechen, wenn Accounts deaktiviert werden, Rollen wechseln oder MFA/Policies angepasst werden. Dedizierte Service Accounts mit klarer Ownership sind für dauerhafte Integrationen stabiler.
