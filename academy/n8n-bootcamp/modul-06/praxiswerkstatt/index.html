MODUL 06 · PRAXISWERKSTATT

Error Handling & Recovery wie im Betrieb

Production ist der Moment, in dem APIs timeouten, 429 liefern, Credentials ablaufen und ein Teil bereits erfolgreich war. Du entwirfst Retry, Recovery, DLQ, Alerts und Runbooks so, dass Fehler kontrolliert bleiben.

CLASSIFYpermanent · transient
RETRYbounded · backoff
ISOLATEDLQ · recovery
OPERATEalert · runbook
Regel: Kein Retry ohne Antwort auf drei Fragen: Ist der Fehler transient? Ist der Side Effect idempotent? Wann hören wir auf?
FALL 01

429 Too Many Requests · Backoff statt Hammering

APIs begrenzen Requests. 429 ist ein Kapazitäts-/Rate-Signal, kein Grund für sofortige 100 Retries.

Quelle: MDN 429 →
Request
→
429
→
Retry-After / Backoff
→
Retry #2
→
Success / DLQ

Deine Aufgabe

  1. Retry-After vorhanden ise ne yaparsın?
  2. Exponential Backoff 1s,2s,4s,8s nasıl sınırlandırılır?
  3. Jitter neden yararlı?
  4. Max retry sonrası ne olur?

Break/Fix

50 parallel executions aynı anda 429 alıp tam 5 saniye sonra birlikte retry ediyor. Thundering herd problemini düzelt.

Musterlösung öffnen

Provider hint varsa kullan; bounded exponential backoff + jitter. Retry exhaustion → recoverable queue/DLQ + alert. Aynı side effect için idempotency key korunur.

FALL 02

400/422 vs 500/503 · Retry sınıfları

Her hata aynı değildir. Request malformed ise tekrar göndermek problemi çözmez; transient server failure ise çözebilir.

Quelle: HTTP Status →
400request fix
422business validation
500server error
503temporary unavailable

Entscheide

  1. 422 invalid email → retry?
  2. 503 → kaç retry?
  3. 401 expired token → refresh?
  4. 403 missing permission → retry?

Break/Fix

Workflow tüm non-2xx cevapları aynı retry policy ile işliyor. Error classifier tasarla.

Musterlösung öffnen

Permanent/request errors → correction/review. Auth expiry may trigger refresh once. Permission/config errors need operator. Transient 429/5xx → bounded retry if side effect safe.

FALL 03

Timeout · sonuç bilinmiyor olabilir

Request timeout oldu diye server side effect yapmadı varsayamazsın.

Quelle: n8n HTTP Request →
POST Order
→
Server processes?
→
Network timeout
→
Unknown Result
→
Reconcile

Deine Aufgabe

  1. Timeout sonrası direkt POST tekrar güvenli mi?
  2. Idempotency key nasıl yardımcı olur?
  3. GET status/reconciliation mümkünse nasıl kullanılır?
  4. Unknown state nasıl loglanır?

Break/Fix

İlk order yaratıldı fakat response kayboldu; retry ikinci order yarattı. Prevention tasarla.

Musterlösung öffnen

Write request unique idempotency key taşır. Timeout sonrası önce same-key retry veya status reconciliation. Unknown outcome explicit state; blind duplicate write yok.

FALL 04

DLQ + Runbook · başarısız item kaybolmaz

Retry bitince veri yok olmamalı; operasyon ekibi ne yapacağını bilmelidir.

Quelle: n8n Error Handling →
Failure
→
Classify
→
Retries exhausted
→
DLQ
→
Operator Replay

DLQ kaydı

  1. correlationId
  2. payload reference
  3. error class/status
  4. attempt count
  5. last error time
  6. safe replay instructions

Runbook

„CRM 503 continues >15 min“ için kim bakar, nereden execution bulur, ne kontrol eder, ne zaman replay yapar?

Musterlösung öffnen

Runbook: symptom → impact → owner → dashboards/log query → credential/API health → recovery steps → replay guard → escalation. DLQ payload secrets içermemeli.

FALL 05 · CAPSTONE

Nightly CRM Sync Incident

Gece sync 4.000 kaydın 2.650'sini işledi. Sonra API 503 verdi; bazı retries 429 oldu. Sabah ekip veri eksikliği görüyor.

4.000 Input
2.650 Done
503
429
↓
Checkpoint · Retry · DLQ · Alert
↓
Reconcile → Safe Replay → Completion Evidence

Incident çöz

  1. Checkpoint hangi kayıtta?
  2. 2.650 tekrar işlenir mi?
  3. Remaining set nasıl bulunur?
  4. 503→429 chain için backoff?
  5. Operator alert içeriği?
  6. Recovery sonrası nasıl completeness kanıtlanır?

Ready to Teach

Retry ile Recovery arasındaki farkı gerçek incident üzerinden anlat.

Referenzlösung öffnen

Checkpoint successful batch boundary'de. Completed IDs/dedupe korunur. Remaining/reconciliation set oluşturulur. Service recovery sonrası bounded replay. Final counts: expected=4000, processed unique=4000, failed unresolved=0.
