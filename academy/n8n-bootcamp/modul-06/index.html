FAILURE TAXONOMY

Nicht jeder Fehler ist derselbe Fehler

02
HTTP VS EXECUTION

Ein HTTP 500 und ein n8n Execution Error sind verwandt, aber nicht identisch

Du kannst Non-2xx bewusst als Daten weiterreichen oder den Node fehlschlagen lassen. Die Wahl beeinflusst Error Workflow, Routing und Observability.

Vertiefung öffnen

Never Error vs technischer Fail

Beim HTTP Request Node kann ein Non-2xx bewusst als Response behandelt werden, damit du Statuscodes selbst klassifizierst. Alternativ lässt du den Node fehlschlagen und nutzt Error Paths/Workflows. Beides ist legitim – entscheidend ist eine konsistente Policy.

03
ERROR PATHS

Continue-on-Fail ist kein „Fehler ignorieren“-Button

Wenn ein Fehlerpfad weiterläuft, muss der Fehler explizit markiert, geloggt und fachlich behandelt werden.

Vertiefung öffnen

Fehler als Daten weiterreichen

Manche Batch-Prozesse sollen bei einem fehlerhaften Item nicht komplett stoppen. Dann wird das Item als failed markiert und die restlichen Items laufen weiter. Später werden Fehler gesammelt, gemeldet oder in Quarantine gelegt.

Item→API Call→ error →failed=true→Quarantine
Anti-Pattern

Continue-on-Fail aktivieren und den Fehler danach vergessen. Das erzeugt „grüne“ Workflows mit verlorenen Daten.

BACKOFF & JITTER

Nicht sofort wieder auf ein kaputtes System feuern

Exponentielles Backoff vergrößert die Wartezeit zwischen Versuchen. Jitter verhindert synchronisierte Retry-Wellen.

Thundering Herd vermeiden

Wenn 1.000 Workflows gleichzeitig 503 bekommen und exakt nach einer Sekunde wiederkommen, trifft die nächste Lastwelle gleichzeitig ein. Random Jitter verteilt die Retries zeitlich.

Beispiel

06
RATE LIMIT

429 ist ein Kapazitätssignal

Rate Limits schützen Provider. Ein guter Workflow respektiert Limits statt sie mit Parallelität zu bekämpfen.

Vertiefung öffnen

Retry-After lesen, Batching anpassen

Provider können Retry-After oder Rate-Limit-Header liefern. Nutze diese Informationen, reduziere Batch Size oder Parallelität und vermeide aggressives Polling.

429→Retry-After→Wait→Retry
Kapazitätsplanung

Wenn 100.000 Items in 60 Requests/min verarbeitet werden müssen, ist das keine kleine Node-Einstellung, sondern eine Laufzeit-/Architekturfrage.

07
TIMEOUT / CIRCUIT BREAKER

Fail fast statt Ressourcen blockieren

Timeouts begrenzen Wartezeit. Circuit Breaker stoppen temporär neue Requests, wenn ein Upstream wiederholt scheitert.

Vertiefung öffnen

Timeout ist Teil des Datenvertrags

Ein externer API-Call darf nicht beliebig lange den gesamten Workflow blockieren. Setze realistische Timeouts und entscheide anschließend: Retry, Async Queue oder Manual Recovery.

Healthy→Failures ↑→Circuit OPEN→Cooldown→Probe
Circuit Breaker

n8n bietet nicht zwingend einen einzelnen „Circuit Breaker“-Button; das Pattern kann über State, Error Rate und Routing modelliert werden.

08
ERROR WORKFLOW

Zentrale Triage für Produktionsfehler

n8n Error Workflows ermöglichen einen einheitlichen Kanal für Fehlerdetails, Alerts und Incident-Korrelation.

Workflow AWorkflow BWorkflow C→Error Trigger→Alert / Log / Ticket
Vertiefung öffnen

Zentrale Fehlerbehandlung reduziert Copy/Paste

Statt in 50 Workflows denselben Slack-/Mail-/Ticket-Code einzubauen, kann ein Error Workflow zentrale Felder normalisieren: Workflow, Execution, Node, Zeit, Fehlermeldung, Severity und Correlation ID.

Secret-safe

Alert enthält niemals vollständige Tokens, API Keys oder sensible Kundendaten. Diagnose braucht Kontext, nicht Credential-Leaks.

Was speichern?

Fachliche ID, sicherer Input oder Pointer, Fehlerklasse, letzte Fehlermeldung, Attempts, Zeit, Workflow-Version und Correlation ID. Keine Secrets.

Replay

RUNBOOK & RECOVERY

Was tun um 03:00 Uhr?

Runbooks beschreiben Diagnose, Mitigation, Recovery und kontrolliertes Replay.

1Detect
2Scope
3Mitigate

Vertiefung öffnen

Runbook ist ausführbar, nicht dekorativ

Es enthält: Symptom, Dashboards/Logs, Owner, bekannte Ursachen, sichere Stop-/Pause-Schritte, Recovery, Replay, Verifikation und Eskalation.

Replay-Risiko: Vor Wiederverarbeitung prüfen, ob vorherige Versuche eventuell doch einen Seiteneffekt erzeugt haben. Timeout bedeutet nicht automatisch „nichts passiert“.
