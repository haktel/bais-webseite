01
ITEM-MODELL

Ein Workflow verarbeitet nicht „irgendwie JSON“

n8n arbeitet mit Items. Ein Item ist eine einzelne Verarbeitungseinheit mit strukturierten Daten.

Item 1 → { "name": "Mina" } Item 2 → { "name": "Jonas" } Item 3 → { "name": "Sara" }
Vertiefung öffnen

Wenn ein Node drei Items erhält, kann er drei Datensätze verarbeiten. Das ist etwas anderes als ein einziges Item, das ein Array mit drei Elementen enthält. Genau dieser Unterschied entscheidet später über Split, Loop, Merge und Aggregate.

02
JSON

Datentypen sicher lesen

Bevor du Expressions oder IF-Regeln baust, musst du erkennen, welcher Typ tatsächlich ankommt.

String"7500"
Number7500
Booleantrue
Array["AI","n8n"]
Object{"name":"Mina"}
Vertiefung öffnen

"7500" und 7500 sehen ähnlich aus, sind aber nicht dasselbe. Typfehler erzeugen falsche Vergleiche, Berechnungen und Validierungsfehler. Production-Workflows konvertieren Typen bewusst statt auf Zufall zu vertrauen.

03
NESTED DATA

Objects und Arrays verschachteln

APIs liefern selten flache Daten. Du musst verschachtelte Strukturen lesen können.

{ "customer": { "name": "Mina", "address": { "city": "Dortmund" } }, "tags": ["AI","Automation"] }
Vertiefung öffnen

Bei nested Objects brauchst du den korrekten Pfad. Bei Arrays musst du zusätzlich entscheiden: Willst du das Array als Ganzes behalten oder jedes Element als eigenes Item weiterverarbeiten?

04
EXPRESSIONS

Dynamische Werte mit $json

Expressions verbinden die Konfiguration eines Nodes mit den Daten des aktuellen Items.

{{$json.email}} {{$json.budget}} {{$json.customer.address.city}}
Vertiefung öffnen

Wenn eine Expression undefined liefert, ist der erste Verdacht nicht „n8n kaputt“, sondern: Existiert das Feld wirklich im Input dieses Nodes? Ist der Pfad korrekt? Ist das aktuelle Item das erwartete?

05
KONTEXT

Daten aus vorherigen Nodes referenzieren

Manchmal brauchst du nicht das aktuelle Item, sondern einen Wert aus einem bestimmten vorherigen Node.

{{ $('Webhook').item.json.body.email }} {{ $('Normalize').item.json.fullName }}
Vertiefung öffnen

Node-Referenzen sind mächtig, aber sie koppeln deinen Workflow stärker an konkrete Node-Namen und Item-Zuordnung. Verwende sie bewusst und dokumentiere, warum der direkte Datenfluss nicht genügt.

06
EDIT FIELDS

Ein internes Schema bauen

Edit Fields / Set eignet sich für transparentes Mapping: Felder auswählen, umbenennen, neue Werte erzeugen.

RAW: first_name → " Mina " mail → " MINA@EXAMPLE.COM " INTERN: fullName → "Mina" email → "mina@example.com"
Vertiefung öffnen

Ein Mapping-Node sollte einen klaren Datenvertrag herstellen. Vermeide, dass jede nachfolgende Node erneut wissen muss, wie fünf verschiedene Quellsysteme ihre Felder nennen.

07
CODE NODE

Code nur dort, wo er wirklich hilft

Ein Code Node ist sinnvoll, wenn Transformationen mit Standard-Nodes unnötig kompliziert werden.

const email = String($json.email).trim().toLowerCase(); const budget = Number($json.budget);
Vertiefung öffnen

Code ist kein Qualitätsbeweis. Standard-Nodes sind oft leichter auditierbar und wartbarer. Code sollte klein, deterministisch, testbar und auf eine klare Aufgabe begrenzt bleiben.

08
MULTI-ITEM

Ein Node, viele Datensätze

Viele Nodes verarbeiten automatisch jedes eingehende Item. Das ist bequem – und gefährlich, wenn du die Item-Anzahl nicht beachtest.

3 Items ↓ Normalize Each Item ↓ 3 normalisierte Items
Vertiefung öffnen

Wenn ein E-Mail-Node 100 Items erhält, kann er potenziell 100 E-Mails senden. Item-Anzahl ist deshalb nicht nur Datenmodellierung, sondern auch Kosten-, Rate-Limit- und Sicherheitsfrage.

09
SPLIT & AGGREGATE

Array auseinandernehmen – Items wieder sammeln

Split verwandelt Elemente in einzelne Items. Aggregate fasst mehrere Items wieder zusammen.

records[3] ↓ SPLIT Item · Item · Item ↓ TRANSFORM Item · Item · Item ↓ AGGREGATE records[3]
Vertiefung öffnen

Das Muster ist extrem häufig bei API-Pagination, CSV/Excel-Importen, CRM-Listen und Batch-Verarbeitung. Entscheidend ist, wann du einzeln handeln und wann du gemeinsam antworten willst.

10
MERGE

Zwei Datenströme kontrolliert zusammenführen

Merge kombiniert Pfade nach einer definierten Logik – nicht einfach „irgendwie wieder zusammen“.

CRM Customer ─┐ ├→ Merge by ID → Combined Record Billing Data ─┘
Vertiefung öffnen

Du musst wissen, ob du nach Position, Schlüssel oder einer anderen Bedingung zusammenführst. Falsches Matching kann Daten verschiedener Kunden vermischen – ein echter Production-Risikofall.

11
DATA QUALITY

Normalisieren, bevor Business-Logik entscheidet

Whitespace, Groß-/Kleinschreibung, Strings statt Numbers und Duplikate werden früh kontrolliert.

" MINA@EXAMPLE.COM " → "mina@example.com" "7500" → 7500 ["AI"," AI ","AI"] → ["AI"]
Vertiefung öffnen

Normalisierung ist kein Kosmetik-Schritt. Sie sorgt dafür, dass nachfolgende IF-Regeln, Datenbank-Queries und Deduplizierung zuverlässig arbeiten.

12
DEBUGGING

Input und Output gegeneinander halten

Bei Datenfehlern suchst du den ersten Node, an dem sich die Struktur unerwartet verändert.

Node Input ↓ Konfiguration / Expression / Code ↓ Node Output ↓ Erwarteter Datenvertrag?
Vertiefung öffnen

Prüfe Item-Anzahl, Feldnamen, Datentypen, nested Pfade, Null/undefined, Array-Inhalt und Output-Schema. Erst danach gehst du zum nächsten Node. Das spart Stunden planloses Herumklicken.
