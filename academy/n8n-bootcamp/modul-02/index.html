01
ITEM-MODELL

Ein Workflow verarbeitet nicht „irgendwie JSON“

n8n arbeitet mit Items. Ein Item ist eine einzelne Verarbeitungseinheit mit strukturierten Daten.

Item 1 → { "name": "Mina" } Item 2 → { "name": "Jonas" } Item 3 → { "name": "Sara" }
Vertiefung öffnen

Items bestimmen, wie oft deine Logik wirklich läuft

In n8n ist ein Item keine hübsche Anzeige, sondern eine Verarbeitungseinheit. Viele Nodes arbeiten automatisch einmal pro Item. Drei Items können also drei API-Aufrufe, drei E-Mails oder drei Datenbank-Updates bedeuten. Ein einziges Item mit einem Array aus drei Elementen verhält sich dagegen komplett anders.

1 Item mit Array

Datentypen sicher lesen

Bevor du Expressions oder IF-Regeln baust, musst du erkennen, welcher Typ tatsächlich ankommt.

Datentypen sind Business-Logik

"7500" ist ein String, 7500 eine Number. Das ist nicht akademisch: Budget-Vergleiche, Summen, Sortierung und Validierung können unterschiedliche Ergebnisse liefern. Gleiches gilt für "false" versus false oder "2026-08-30" versus ein echtes Datumsobjekt in späterer Verarbeitung.

Grenzwert-Test

Wenn die Regel budget >= 5000 lautet, teste mindestens 4999, 5000, 5001, "5000", null und "abc".

03
NESTED DATA

Objects und Arrays verschachteln

APIs liefern selten flache Daten. Du musst verschachtelte Strukturen lesen können.

{ "customer": { "name": "Mina", "address": { "city": "Dortmund" } }, "tags": ["AI","Automation"] }
Vertiefung öffnen

APIs liefern Hierarchien, keine Tabellenzeilen

Ein Kunde kann Adresse, Ansprechpartner, Bestellungen und Tags als verschachtelte Objects und Arrays enthalten. Du musst unterscheiden: Welcher Teil beschreibt ein Objekt, welcher Teil eine Liste, und welche Ebene soll der nächste Node erhalten?

Ein Developer referenziert $json.city, obwohl die API customer.address.city liefert. Ergebnis: undefined. Nicht n8n ist kaputt – der Datenpfad ist falsch.

04
EXPRESSIONS

Dynamische Werte mit $json

Expressions verbinden die Konfiguration eines Nodes mit den Daten des aktuellen Items.

{{$json.email}} {{$json.budget}} {{$json.customer.address.city}}
Vertiefung öffnen

Expressions sind live gebundene Datenpfade

Eine Expression wird zur Laufzeit gegen den aktuellen Datenkontext ausgewertet. Deshalb kann dieselbe Expression in Node A funktionieren und in Node B undefined liefern, wenn Node B einen anderen Input bekommt.

Input{"email":"mina@example.com","budget":7500}
→
Expression{{$json.email}}
→
Outputmina@example.com
SymptomPrüfung
undefinedFeld/Pfad existiert?
falscher DatensatzWelches Item ist aktuell?
alter WertKommt der Wert aus aktuellem oder referenziertem Node?
Expression funktioniert nur im TestTestdaten vs Production Input vergleichen
Professional Rule

Nie eine Expression blind kopieren. Öffne zuerst den Input, identifiziere exakt den Pfad und teste mit mindestens zwei unterschiedlichen Datensätzen.

REALER FALL · STEPSTONE

Wie dieses Prinzip in Production sichtbar wird

Die Stepstone Group beschreibt mehr als 700 aktive n8n Workflows in Produktion und 2–3 Millionen verarbeitete jobbezogene Dokumente pro Monat. Bei wachsender Nutzung wurden klare Workflow- und Credential-Berechtigungen, Execution-Monitoring, Ownership und eine getrennte Security-Umgebung wichtig. In einem konkreten Mapping-Fall wurden täglich 60–70 manuelle Contract-Mappings durch einen Workflow auf rund 20 Sekunden für den gesamten Tagesstapel reduziert.

Übertrag auf diesen Lernpunkt

Expressions sind die verbindende Schicht zwischen Input und Node-Parameter. Vor jeder Expression wird der reale Node-Input geprüft, nicht aus Erinnerung geraten.

05
KONTEXT

Daten aus vorherigen Nodes referenzieren

Manchmal brauchst du nicht das aktuelle Item, sondern einen Wert aus einem bestimmten vorherigen Node.

{{ $('Webhook').item.json.body.email }} {{ $('Normalize').item.json.fullName }}
Vertiefung öffnen

Direkter Datenfluss oder explizite Node-Referenz?

$json liest den aktuellen Input. Eine Referenz wie {{ $('Webhook').item.json.body.email }} springt gezielt zu einem anderen Node. Das kann sinnvoll sein, erhöht aber die Kopplung: Umbenennen, Branches und Multi-Item-Situationen können die Referenz schwerer verständlich machen.

Aktueller PfadNormalize → IF → Email{{$json.email}}
DirektreferenzEmail greift zurück auf Webhook{{ $('Webhook').item.json.body.email }}
Bevorzugt

Daten so transformieren, dass der direkte Flow alles Benötigte enthält.

Gezielt einsetzen

Node-Referenz, wenn ein stabiler, bewusst dokumentierter Wert aus einem früheren Schritt benötigt wird.

Refactoring-Fall: Node Webhook wird in Website Lead Trigger umbenannt. Direkte Referenzen müssen nachvollziehbar angepasst werden; sauberer Datenfluss reduziert solche Abhängigkeiten.

EDIT FIELDS

Ein internes Schema bauen

Edit Fields / Set eignet sich für transparentes Mapping: Felder auswählen, umbenennen, neue Werte erzeugen.

RAW: first_name → " Mina " mail → " MINA@EXAMPLE.COM " INTERN: fullName → "Mina" email → "mina@example.com"
Vertiefung öffnen

Mapping entkoppelt Quellsysteme von deiner Business-Logik

CRM A nennt das Feld mail, Formular B nennt es emailAddress, API C liefert contact.email. Wenn jede spätere Node alle Varianten kennen muss, wird der Workflow fragil. Ein früher Mapping-Schritt erzeugt ein internes kanonisches Schema.

→ NORMALIZE →

07
CODE NODE

Code nur dort, wo er wirklich hilft

Ein Code Node ist sinnvoll, wenn Transformationen mit Standard-Nodes unnötig kompliziert werden.

const email = String($json.email).trim().toLowerCase(); const budget = Number($json.budget);
Vertiefung öffnen

Low-code bedeutet nicht „kein Code“ – sondern Code mit Absicht

Ein Code Node ist stark, wenn du mehrere zusammenhängende Transformationen sauber in einer kleinen Funktion ausdrücken kannst. Er wird problematisch, wenn darin API-Aufrufe, Business-Regeln, Logging und zehn Seiteneffekte gleichzeitig versteckt werden.

Gut begrenzt
const email =
 String($json.email)
 .trim()
 .toLowerCase();

return {json:{...$json,email}};
Riskant

// DB write
// retry
// parsing
// business rules
// secrets ...

08
MULTI-ITEM

Ein Node, viele Datensätze

Viele Nodes verarbeiten automatisch jedes eingehende Item. Das ist bequem – und gefährlich, wenn du die Item-Anzahl nicht beachtest.

3 Items ↓ Normalize Each Item ↓ 3 normalisierte Items
Vertiefung öffnen

Multi-Item-Verarbeitung multipliziert Seiteneffekte

100 eingehende Items können 100 HTTP-Requests, 100 E-Mails oder 100 Datensätze erzeugen. Deshalb musst du vor Nodes mit externem Seiteneffekt wissen, wie viele Items ankommen und ob das Zielsystem diese Last erlaubt.

09
SPLIT & AGGREGATE

Array auseinandernehmen – Items wieder sammeln

Split verwandelt Elemente in einzelne Items. Aggregate fasst mehrere Items wieder zusammen.

records[3] ↓ SPLIT Item · Item · Item ↓ TRANSFORM Item · Item · Item ↓ AGGREGATE records[3]
Vertiefung öffnen

Split und Aggregate verändern die Granularität

Split macht aus einer Liste einzelne Verarbeitungseinheiten. Aggregate sammelt Ergebnisse wieder ein. Das Muster erscheint bei CSV-Import, API-Pagination, Produktlisten, Bestellungen und Reporting ständig.

records[3]
→ SPLIT →
Item AItem BItem C
→ PROCESS →
results[3]
1API liefert 100 Produkte als Array.
2Split: jedes Produkt wird ein Item.
3Filter/Transform pro Produkt.
4Aggregate: ein Report mit allen Ergebnissen.
Entscheidungsfrage

Muss die nächste Aktion pro Datensatz ausgeführt werden? Dann splitten. Braucht die nächste Aktion die Gesamtheit, z. B. eine Zusammenfassung? Dann aggregieren.

10
MERGE

Zwei Datenströme kontrolliert zusammenführen

Merge kombiniert Pfade nach einer definierten Logik – nicht einfach „irgendwie wieder zusammen“.

CRM Customer ─┐ ├→ Merge by ID → Combined Record Billing Data ─┘
Vertiefung öffnen

Merge ist ein Join – und damit eine Datenintegritätsfrage

Wenn CRM-Daten und Billing-Daten zusammengeführt werden, brauchst du einen stabilen Schlüssel wie customerId. Merge nach Position ist nur sicher, wenn die Reihenfolge garantiert identisch bleibt. Sonst verknüpfst du möglicherweise Rechnung von Kunde A mit Stammdaten von Kunde B.

CRMC-100 · MinaC-200 · Jonas
customerId
MERGE
customerId
BillingC-200 · 89 €C-100 · 129 €
Falsch: Position

Zeile 1 mit Zeile 1 verbinden, obwohl die Reihenfolge unterschiedlich ist.

Richtig: stabiler Key

customerId, orderId oder ein anderer eindeutiger fachlicher Schlüssel.

Production-Risiko: Falscher Merge kann nicht nur einen technischen Fehler erzeugen, sondern vertrauliche Kundendaten falsch zuordnen. Deshalb gehören Matching-Regeln und Testfälle in die Dokumentation.

DEBUGGING

Input und Output gegeneinander halten

Bei Datenfehlern suchst du den ersten Node, an dem sich die Struktur unerwartet verändert.
