Transienter Datenfluss vs persistenter Zustand

$json lebt im aktuellen Workflow-Durchlauf. Persistence lebt über diesen Durchlauf hinaus und beeinflusst spätere Executions.

State beantwortet die Frage: „Was wusste das System gestern?“

Wenn ein Webhook heute dasselbe eventId erneut sendet, kann dein Workflow nur dann erkennen, dass dieses Ereignis bereits verarbeitet wurde, wenn diese Information außerhalb der ursprünglichen Execution gespeichert wurde.

Execution #1→eventId speichern→ ZEIT →Execution #2→eventId wiederfinden
Ohne State

Jede Execution wirkt wie der erste Kontakt mit den Daten.

Mit State

Der Workflow kann vergleichen, fortsetzen, deduplizieren und inkrementell arbeiten.

Reales Problem: Payment-Provider retried denselben Webhook. Ohne persistenten Dedupe-Key könnte dein Workflow dieselbe Rechnung, E-Mail oder Buchung ein zweites Mal erzeugen.

Data Table ist echter State – aber keine Universal-Datenbank

Data Tables sind sehr gut für Lookup-Tabellen, Dedupe-Keys, kleine bis mittlere State-Mengen, Konfiguration und Kontrolltabellen. Für hochkomplexe relationale Modelle, schwere Analytics oder echte Multi-Table-Transaktionen ist PostgreSQL/MySQL oft die bessere Architektur.

SCHEMA & KEYS

Fachliche Identität von technischer Row-ID trennen

Ein stabiles Datenmodell beginnt damit, dass jede Entität einen zuverlässigen Domain-Key besitzt.

Vertiefung öffnen

Warum nicht Name oder E-Mail als universeller Key?

Namen sind nicht eindeutig. E-Mail-Adressen können sich ändern. Gute Domain-IDs werden vom Quellsystem stabil vergeben oder intern als eindeutige Business-ID erzeugt.

Guter Key

customerId = C-1042orderId = ORD-88eventId = evt_abc123

Schwacher Key

name = Mina Yilmaztimestamp onlyarray position = 3
Schema Contract

Definiere Name, Datentyp, Nullability, Bedeutung, Quelle und Key-Funktion jedes kritischen Felds.

UPSERT

Update wenn vorhanden – sonst Insert

Upsert ist eines der wichtigsten Patterns für Synchronisation und wiederholbare Integrationen.

customerId=C-1042

Incoming State

→ UPSERT →
Match gefunden

Kein Match

Vertiefung öffnen

Upsert verhindert blindes „immer neue Row“

Wenn CRM C-1042 zuerst als lead und später als qualified liefert, willst du in vielen Fällen dieselbe fachliche Entität fortschreiben – nicht zwei Kunden erzeugen.

Execution #1→C-1042 · lead→ später →Execution #2→C-1042 · qualified
Race Condition

Ein manuelles Get → IF → Insert kann bei parallelen Executions Duplikate erzeugen. Echte DB-Unique-Constraints/Upsert-Semantik sind für harte Konsistenz stärker.

TRANSACTIONS

Alles oder nichts

Wenn mehrere Datenbankänderungen gemeinsam konsistent sein müssen, brauchst du Transaction-Denken.

BEGIN
Order INSERT
Stock UPDATE
COMMIT
bei Fehler: ROLLBACK
Vertiefung öffnen

Partial State vermeiden

Stell dir vor: Order wurde gespeichert, Stock-Update scheitert. Ohne Transaction kann die Datenbank in einem fachlich unmöglichen Zwischenzustand bleiben.

BEGIN→Operation A→Operation B→ Erfolg →COMMIT· Fehler →ROLLBACK
Grenze

Eine SQL-Transaction kann nicht automatisch eine externe E-Mail oder SaaS-API zurückrollen. Dafür brauchst du Saga/Compensation-Patterns.

Backup ohne Restore-Test ist nur Hoffnung

Definiere, welche Daten gesichert werden, wie oft, wie lange und wie ein Restore tatsächlich funktioniert. Prüfe außerdem, ob personenbezogene Daten nach Ablauf der fachlichen/rechtlichen Aufbewahrungsfrist gelöscht oder anonymisiert werden müssen.

Schema Migration

score von String zu Number? Downstream Expressions, Reports und Filters müssen angepasst und getestet werden.

Retention

Dedupe-Events eventuell 30/90 Tage; Kundendaten je nach Zweck anders. Nicht „für immer“ als Default.

Migration-Fall: Feld customerId wird umbenannt. Zehn Workflows referenzieren den alten Namen. Ohne Versionierung und Migrationsplan brechen Integrationen verteilt.

Zwei Executions – derselbe State

Dieser Lab verwendet echte n8n Data Tables. Führe A → B aus: dieselbe fachliche Customer-ID wird in einer späteren Execution wiedererkannt und per Upsert aktualisiert. Führe C → D aus: dasselbe Event wird beim zweiten Mal als Duplicate erkannt.

Reihenfolge wichtig

A → B beweist Upsert über zwei getrennte Executions. C → D beweist persistente Deduplizierung.

A · First State

  1. Starte A.
  2. Notiere technische Row-ID, customerId, createdAt und updatedAt.
  3. Erkläre, warum die Row nach Ende der Execution nicht verschwindet.

B · Upsert Across Executions

  1. Starte B direkt nach A.
  2. Vergleiche Row-ID: dieselbe fachliche Row soll fortgeschrieben werden.
  3. Prüfe status qualified und score 85.
  4. Erkläre INSERT vs UPDATE vs UPSERT.

C · Event First Delivery

  1. Starte C.
  2. Event-ID darf noch nicht existieren.
  3. Row wird gespeichert und duplicate=false.

D · Duplicate Replay

  1. Starte D nach C.
  2. Dieselbe Event-ID existiert bereits.
  3. Der Workflow muss duplicate=true und inserted=false liefern.
  4. Erkläre, welche doppelte Business-Aktion dadurch verhindert werden könnte.
