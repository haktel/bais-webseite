MODUL 07 · PRAXISWERKSTATT

State & Persistence ohne doppelte oder verlorene Daten

Production Workflows brauchen Gedächtnis: Domain Keys, Upsert, Dedupe, Cursor, Transactions, Retention und Recovery. Hier entscheidest du, wann ein Workflow sicher fortsetzen darf.

IDENTIFYDomain Key
PERSISTCRUD · Upsert
CHECKPOINTCursor · Dedupe
RECOVERBackup · Replay
Regel: State erst dann fortschreiben, wenn die zugehörige Arbeit nachweislich erfolgreich abgeschlossen ist.
FALL 01

Upsert · Customer wird aktualisiert statt dupliziert

Wenn derselbe fachliche Kunde erneut kommt, entscheidet ein stabiler Domain Key, ob INSERT oder UPDATE erfolgt.

Quelle: n8n Data Table →
customerId=C-1
→
Lookup
→
exists?
→
Update / Insert
→
1 canonical row

Deine Aufgabe

  1. Email neden kötü primary/domain key olabilir?
  2. customerId değişmezse hangi alanlar update edilir?
  3. Race condition ile iki insert nasıl oluşabilir?
  4. Unique constraint neden önemlidir?

Break/Fix

Aynı müşteri iki paralel execution'da ilk kez gelir. İkisi de lookup'ta bulamaz. Duplicate'i önle.

Musterlösung öffnen

Business domain key için unique constraint/atomic upsert kullan. "Önce SELECT sonra INSERT" tek başına concurrency altında yeterli değildir.

FALL 02

Dedupe · Event bir kez işlenir

Webhook provider aynı event'i tekrar gönderebilir. Persistence layer processed event IDs'i hatırlamalıdır.

Quelle: n8n Execution Data →
eventId=E-42
→
seen?
→ no →
Process
→
persist E-42

Deine Aufgabe

  1. eventId kaç gün tutulmalı?
  2. Dedupe row ne zaman yazılır?
  3. Process başarılı, dedupe write fail olursa?
  4. Payload hash ne zaman ek sinyal olabilir?

Break/Fix

Mail gönderildi ama eventId kaydı yazılamadı; provider retry etti ve mail tekrar gitti. Atomicity/recovery tasarla.

Musterlösung öffnen

Side effect + state commit arasında tutarlılık tasarlanmalı. Mümkünse transactional/outbox/idempotent downstream. En azından status=processing/completed gibi recoverable state kullan.

FALL 03

Incremental Sync · Cursor yalnız başarıdan sonra

Bir API'den updated_after ile her gece değişen kayıtlar çekiliyor.

Quelle: n8n Looping →
cursor=T0
→
Fetch changes
→
Process all
→
Verify
→
cursor=T1

Deine Aufgabe

  1. 1000 kaydın 800'ü işlendi, sonra fail. Cursor T1 olur mu?
  2. Pagination cursor ile business sync cursor farkı?
  3. Late-arriving data nasıl ele alınır?
  4. Overlap window gerekir mi?

Break/Fix

Cursor işlem başında güncellendi; fail sonrası 200 kayıt bir daha çekilmedi. Veri kaybını düzelt.

Musterlösung öffnen

Business checkpoint yalnız tamamlanan unit sonrası commit edilir. Gerekirse overlap + dedupe ile geç gelen kayıtlar güvenli yakalanır.

FALL 04

Transaction · yarım business update kabul edilir mi?

Order kaydı ve inventory reservation birlikte başarılı olmalı; aksi durumda tutarsızlık oluşur.

Quelle: PostgreSQL Transactions →
BEGIN
→
Order UPDATE
→
Inventory UPDATE
→
COMMIT
↔ fail
ROLLBACK

Deine Aufgabe

  1. Atomicity nedir?
  2. İki farklı SaaS API transaction paylaşabilir mi?
  3. Distributed transaction yoksa compensation nedir?
  4. Retry hangi state'ten başlar?

Break/Fix

CRM update başarılı, ERP update başarısız. Compensation veya reconciliation tasarla.

Musterlösung öffnen

Tek DB içinde transaction kullanılabilir. Farklı sistemlerde Saga/compensating action/reconciliation gerekir; business state explicit tutulur.

FALL 05 · CAPSTONE

Persistent Customer Sync + Retention + Backup

CRM↔ERP sync customer state, dedupe events ve sync cursor tutuyor. Audit retention ve restore planı da isteniyor.

Pflichtaufgabe

  1. Tabloları ve key'leri tasarla.
  2. Dedupe retention belirle ve gerekçelendir.
  3. Cursor commit boundary tanımla.
  4. Backup sıklığı/RPO tasarla.
  5. Restore testi nasıl yapılır?
  6. 6 failure/recovery test yaz.

Ready to Teach

Persistence neden sadece „veriyi DB'ye yazmak“ değildir? Consistency, lifecycle ve recovery üzerinden anlat.

Referenzlösung öffnen

customers(customerId unique), processed_events(eventId unique,processedAt), sync_state(jobName,cursor,updatedAt), audit_events(traceId,status). Retention purpose-based; backup şifreli/erişim kontrollü; restore düzenli test edilir.
