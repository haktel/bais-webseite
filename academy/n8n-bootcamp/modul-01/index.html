01
MENTAL MODEL

Was n8n wirklich ist

n8n ist eine Orchestrierungs- und Integrationsplattform: Ein Ereignis startet einen kontrollierten Datenfluss zwischen Systemen.

Ereignis
→
Workflow
→
Ergebnis
Vertiefung öffnen

Was passiert in einem echten Unternehmen?

n8n sitzt häufig zwischen bereits vorhandenen Systemen. Ein Formular, Ticket oder Security-Event löst etwas aus; n8n liest Daten, ruft APIs auf, trifft regelbasierte Entscheidungen und schreibt das Ergebnis in andere Systeme zurück. Es ist damit eher Orchestrator als Ersatz für CRM, Datenbank oder Identity-System.

LIFECYCLE

Vom Prozess zum Workflow

Ein professioneller Workflow beginnt mit Prozessverständnis und endet nicht beim ersten grünen Lauf.

DISCOVERY → DESIGN → BUILD → TEST → SECURE → DEPLOY → MONITOR → MAINTAIN
Vertiefung öffnen

Ein Workflow ist ein Produkt mit Lebenszyklus

Discovery klärt Prozess, Volumen, Nutzer, Systeme und Risiko. Design definiert Datenfluss, Verantwortlichkeiten und Fehlerpfade. Build setzt die Logik um. Test prüft Happy Path, Grenzwerte und Fehler. Secure reduziert Rechte und schützt Secrets. Deploy bringt eine kontrollierte Version live. Monitor erkennt Störungen. Maintain behandelt API-Änderungen und neue Anforderungen.

Discovery→Design→Build→Test→Secure→Deploy→Monitor

04
DATENMODELL

Items und JSON

n8n transportiert strukturierte Datensätze. JSON ist dabei eines der wichtigsten Formate.

Item 1 → {"name":"Anna","budget":7500} Item 2 → {"name":"Mehmet","budget":3200}
Vertiefung öffnen

JSON ist der Vertrag zwischen Systemen

APIs und Webhooks liefern nicht „nur Text“, sondern strukturierte Daten. Ein Feld kann String, Number, Boolean, Array, Object oder null sein. Für n8n ist entscheidend, ob ein Node ein Item mit einem Array oder mehrere Items erhält – das verändert spätere Loops, E-Mails und API-Aufrufe.

Ein Item mit Array
{"customers":[{"id":1},{"id":2}]}
Zwei Items
Item 1 {"id":1}
Item 2 {"id":2}
Realer Alltag

Ein CRM liefert 500 Kontakte als Array. Bevor du 500 E-Mails sendest, musst du wissen, ob du splitten, filtern, batchen oder aggregieren willst.

Gefahr

Ein unerwartetes Array kann aus „eine E-Mail senden“ plötzlich „500 E-Mails senden“ machen.

Mini-Übung

In {"company":"BAIS","active":true,"services":["AI","n8n"]}: company=String, active=Boolean, services=Array.

05
DYNAMISCHE DATEN

Expressions und Datenreferenzen

Expressions lesen Werte dynamisch aus dem aktuellen oder einem anderen Node-Kontext.

{{$json.name}} → aktueller Name {{$json.budget}} → aktuelles Budget
Vertiefung öffnen

Expressions sind Datenzugriff, keine Magie

{{$json.name}} funktioniert nur, wenn im aktuellen Item tatsächlich ein Feld name existiert. Nach einer Transformation kann das Feld anders heißen oder tiefer verschachtelt sein. Deshalb prüft ein Professional immer zuerst den Input der betroffenen Node.

Input
{"customer":{"name":"Mina"}}
Korrekt
{{$json.customer.name}}
Node Input prüfen→Pfad lesen→Expression testen→Output kontrollieren
Realer Fehler

Eine API-Version ändert email zu contact.email. Der Workflow läuft weiter, aber deine Expression liefert undefined. Ohne Datenprüfung suchst du am falschen Ort.

06
HTTP

Webhooks als Eingangstor

Ein Webhook ist ein HTTP-Endpunkt. Externe Systeme können damit einen Workflow ereignisgesteuert starten.

POST /webhook/bais-academy-modul-01 Content-Type: application/json ↓ {"name":"Max","email":"max@example.com","budget":7500}
Vertiefung öffnen

Webhook = öffentlicher Eingang mit Vertrag

Ein Webhook besteht nicht nur aus einer URL. Zum Vertrag gehören HTTP-Methode, Pfad, Headers, Content-Type, Body-Schema, Authentifizierung, erwartete Statuscodes und Timeout-Verhalten. Production muss außerdem Rate Limits, Validation und Missbrauch berücksichtigen.

REQUEST
POST /webhook/order
Content-Type: application/json

{"orderId":"A-1042","total":129.90}
RESPONSE
200 OK
{"ok":true,"status":"accepted"}
Test URL

/webhook-test/... ist für die Entwicklung und temporäres Listening.

Production URL

/webhook/... gehört in reale Anwendungen und benötigt einen aktiven Workflow.

Realer Alltag

Shop-Systeme, Stripe-Events, CRM-Callbacks, GitHub-Events und Website-Formulare starten Prozesse über Webhooks. Die meisten Fehler entstehen durch falsche Methode, falschen Body oder fehlende Authentifizierung.

07
OBSERVABILITY

Executions verstehen

Jeder konkrete Workflow-Lauf ist eine Execution. Sie ist deine wichtigste Spur beim Debugging.

Execution #1842 Webhook OK Validate OK Transform OK IF OK Respond OK
Vertiefung öffnen

Execution = dein forensischer Laufzettel

Eine Execution zeigt, welcher konkrete Request wann durch welche Nodes gelaufen ist und wo er scheiterte. Ohne Execution ist der Trigger vermutlich nie erreicht worden. Mit Execution kannst du den ersten fehlerhaften Schritt isolieren.

1 · Webhook OK
2 · Validate OK
3 · HTTP Request 401
4 · Database nicht ausgeführt
Keine Execution

URL, DNS, Methode, Workflow-Aktivierung, Reverse Proxy und Request prüfen.

Execution vorhanden

Erste rote Node öffnen: Input → Parameter → Error → HTTP-Status → Output.

Praxis

Ein Kunde meldet „Formular geht nicht“. Statt alles neu zu bauen suchst du die konkrete Execution-ID und kannst reproduzierbar feststellen, ob das Problem im Browser, Backend, n8n oder externen API liegt.

08
SECRETS

Credentials und Environment Variables

API Keys, Tokens und Passwörter gehören nicht als Klartext in öffentliche Dateien oder frei sichtbare Workflow-Felder.

Workflow → Credential Store → API Environment → API_BASE_URL / ENVIRONMENT / Konfiguration
Vertiefung öffnen

Credentials sind Produktionsvermögen

Ein API Key kann Kundendaten lesen, E-Mails senden oder Daten löschen. Deshalb gehören Credentials in einen Secret-/Credential-Mechanismus und erhalten nur die Scopes, die ein Workflow tatsächlich braucht. Development und Production sollten unterschiedliche Zugangsdaten besitzen.

Workflow→Credential Store→kurzlebiges / begrenztes Secret→API
REALER FALL · STEPSTONE

Skalierung macht Credential-Management sichtbar

Stepstone beschreibt, dass bei hunderten Workflows ein gemeinsamer Master-Account und geteilte Credentials nicht mehr tragfähig waren. Der Enterprise-Ausbau brachte unter anderem Rollen, Credential-/Workflow-Permissions und externe Secret-Verwaltung in den Fokus.

Quelle: n8n Case Study →
3.000Mitarbeitende im Rollout
Nie tun

API Key in HTML, Screenshot, Git-Repository, Chat oder Execution-Log kopieren. Bei Leak: Key sofort rotieren und Audit durchführen.

09
BETRIEBSMODELL

Cloud vs Self-hosted

Managed Cloud reduziert Betriebsaufwand. Self-hosted bietet mehr Kontrolle, verschiebt aber Verantwortung zu dir.

Vertiefung öffnen
BereichManaged CloudSelf-hosted
PatchenAnbieter übernimmt vieldu planst Updates und Wartungsfenster
Backupsabhängig vom Angebotdu definierst DB-/Config-Backup und Restore-Test
Netzwerkweniger KontrolleReverse Proxy, Firewall, TLS, private Netze möglich
SecretsPlattformmechanismeneigene Policy und Rotation
Monitoringteilweise inklusivedu brauchst Healthchecks, Logs und Alerts
Internet→TLS / Reverse Proxy→n8n→DB / APIs
Unser Labor

BAIS nutzt eine eigene n8n-Instanz auf RepoCloud. Dadurch haben wir Kontrolle über API-Deployment und Workflows – aber auch Verantwortung für Keys, Verfügbarkeit, Backups und Update-Strategie.

Entscheidungsfrage

Self-hosted ist nicht automatisch „sicherer“. Es ist nur kontrollierbarer, wenn Betrieb und Security tatsächlich professionell umgesetzt werden.

SECURITY ARCHITECTURE

Security Boundary

Externe Daten sind untrusted. Eine Vertrauensgrenze prüft Input, Identität, Rechte oder Bot-Schutz, bevor interne Systeme handeln.

INTERNET [UNTRUSTED] ↓ Cloudflare / Validation / Policy ↓ n8n ↓ Database / API / E-Mail
Vertiefung öffnen

Trust Boundary: Wo endet Vertrauen?

Browser, externe Webhooks und Partner-APIs gelten zunächst als untrusted. Bevor Daten interne Workflows, Datenbanken oder privilegierte APIs steuern, werden Schema, Authentizität, Berechtigungen, Größe und erlaubte Werte geprüft.

DEBUGGING

Nicht raten – Datenfluss verfolgen

Professionelles Debugging folgt einer festen Reihenfolge.

INPUT → TRIGGER → EXECUTION → NODE → OUTPUT
Vertiefung öffnen

Debugging-Matrix statt planloses Klicken

Gehe immer vom beobachtbaren Symptom zur Schicht: Erreicht der Request das System? Entsteht eine Execution? Wo ist die erste Abweichung? Welcher Statuscode kommt? Welche Daten lagen unmittelbar davor an?
