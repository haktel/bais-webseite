MODUL 01 · PRAXISWERKSTATT

Reale Produktionsfälle zerlegen, planen und erklären

Hier wird nicht geklickt, bis etwas irgendwie funktioniert. Jeder Fall beginnt mit einem real dokumentierten Einsatzmuster. Danach musst du Datenfluss, Failure Modes, Security Boundary und Production-Reife selbst entwerfen. Erst danach öffnest du die Musterlösung.

1 · ANALYSIERENWas war das reale Problem?
2 · MODELLIERENTrigger → Daten → Action
3 · BREAK/FIXFehler absichtlich erzeugen
4 · ERKLÄRENWie würdest du es unterrichten?
Regel: Musterlösung erst öffnen, nachdem du deine eigene Lösung auf Papier, Whiteboard oder n8n Canvas skizziert hast.
FALL 01

Delivery Hero · Account-Recovery-Automation

Delivery Hero beschreibt öffentlich eine n8n-Automation, die wiederkehrende IT-Account-Recovery-Aufgaben automatisierte und ungefähr 200 Arbeitsstunden pro Monat einsparte.

Deine Aufgabe

  1. Welche Inputs braucht der Workflow mindestens?
  2. Was ist Trigger, was Action, was Security Boundary?
  3. Wo darf ein automatischer Reset enden und wo braucht es Human Approval?
  4. Welche Execution-Daten würdest du für Audit speichern?

Break/Fix

Provoziere drei Fehler: unbekannte E-Mail, deaktivierter Account, Downstream-API liefert 503. Definiere für jeden Fehler die erwartete Route.

Musterlösung öffnen

Architektur

Trigger: authentifizierter Request oder Helpdesk Event. Validation: Benutzer-ID, Status, Berechtigung. Action: nur erlaubte Recovery-Aktion. Audit: requestId, actor, target, result, timestamp – keine Passwörter oder Tokens.

FALL 02

Stepstone · Millionen Dokumente pro Monat

Stepstone berichtet über n8n-Verarbeitung von ungefähr 2–3 Millionen jobbezogenen Dokumenten pro Monat. Das macht Item-Modell, Batching und Failure Isolation unmittelbar relevant.

Quelle: n8n Case Study →
1 Itemein Datensatz

100.000mehrere Runs

Deine Aufgabe

  1. Warum ist „ein Array mit 10.000 Einträgen“ nicht dasselbe wie 10.000 Items?
  2. Wo würdest du Batching einbauen?
  3. Wie verhinderst du, dass ein kaputtes Dokument den gesamten Lauf zerstört?
  4. Welche KPI misst du: documents/min, failure rate, duration oder alle?

Break/Fix

Item 4.231 enthält ein unerwartetes Schema. Zeichne den Pfad, damit Item 1–4.230 und 4.232+ weiter verarbeitet werden können.

Musterlösung öffnen

Input wird früh normalisiert und validiert. Große Mengen werden in kontrollierte Batches zerlegt. Dokumentfehler gehen in einen separaten Failure-/DLQ-Pfad mit correlationId. Metriken: throughput, error rate, p95 duration, backlog und retry count.

FALL 03

Vodafone · Low-code + Code als modulare Plattform

Vodafone beschreibt öffentlich den Einsatz von n8n für produktive Automationen mit einer Kombination aus visuellen Workflows und Code. Das ist ein gutes Beispiel für klare Component Boundaries.

Quelle: n8n Case Study →
Visual NodesOrchestration
ExpressionsMapping
Code Nodekomplexe Transformation
Sub-WorkflowReuse

Deine Aufgabe

  1. Welche Logik gehört in IF/Switch, welche in Code?
  2. Wann wird ein wiederkehrender Teil ein Sub-Workflow?
  3. Warum ist ein 300-Zeilen-Code-Node schlecht wartbar?
  4. Wie würdest du Ownership dokumentieren?

Break/Fix

Drei Workflows enthalten denselben Normalisierungscode, aber einer wurde anders geändert. Beschreibe, wie Copy-Paste-Divergenz entsteht und wie du sie beseitigst.

Musterlösung öffnen

Einfache Routing-Regeln bleiben sichtbar in IF/Switch. Komplexe, testbare Transformation darf in Code. Wiederverwendbare Fachlogik wird als Sub-Workflow mit Input-/Output-Contract extrahiert. Owner, Version und Caller-Liste gehören zur Component-Dokumentation.

Excel liefert customer_id, BigQuery liefert customerId, PDF-Parser liefert gar keine ID. Entwirf Normalisierung + Reject-Regel.

Musterlösung öffnen

  "traceId":"..."

Source-spezifische Nodes transformieren in ein stabiles internes Schema. Fehlende Pflicht-ID → validation/review statt stiller Weiterverarbeitung.

Deine Aufgabe

  1. Welche Datentypentscheidung muss direkt nach dem Trigger erfolgen?
  2. Wie sieht ein internes Message-Schema aus?
  3. Wo gehört Transkription hin?
  4. Was passiert bei unbekannter Intent-Klasse?

Break/Fix

Voice Note hat keinen Text, CRM benötigt aber messageText. Baue Fallback/Transcription-Pfad und einen Fehlerfall für nicht transkribierbare Audio-Datei.

Musterlösung öffnen

Nach Trigger zunächst Media Type bestimmen. Text direkt normalisieren, Audio erst transkribieren. Beide Pfade liefern dasselbe interne Schema. Unbekannte Intent → Human Review/General Queue statt zufälligem CRM-Update.

Kundenfall

Ein mittelständischer IT-Dienstleister bekommt Leads per Website, E-Mail und CSV. Heute kopiert ein Mitarbeiter Daten manuell ins CRM. Ziel: automatisieren, aber ungültige Daten und hohe Budgets müssen kontrolliert behandelt werden.

  1. Definiere Trigger pro Quelle.
  2. Erstelle internes Lead-Schema.
  3. Definiere Validation + Dedupe.
  4. Budget ≥ 10.000 € → Human Approval.
  5. CRM 429/5xx → Retry/Backoff.
  6. Erstelle Audit-/Monitoring-Felder.
  7. Schreibe fünf Acceptance Tests.

Ready to Teach

Erkläre den gesamten Entwurf in maximal fünf Minuten, ohne n8n-UI zu zeigen. Wenn du Prozess, Datenfluss, Risiken und Betrieb erklären kannst, hast du das Architekturprinzip verstanden.

Acceptance Tests

  1. Valid lead under 10k creates/updates exactly one CRM record.
  2. Duplicate lead does not create a second record.
  3. Invalid email is rejected before CRM.
  4. Budget 10k+ never reaches CRM before approval.
  5. 429 retries are bounded; exhausted retries create operational alert/recovery item.
