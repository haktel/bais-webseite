01
GRUNDLAGEN

Direkte und indirekte Prompt Injection

Der Angreifer muss nicht mit dem Chat interagieren — es reicht, ein Dokument zu platzieren, das das System irgendwann liest.

Wo kommt die Anweisung her?
Direkt im Chat/Prompt eingegebenDirekte Prompt Injection
Versteckt in Dokument, Webseite, E-MailIndirekte Injection – höheres RAG-Risiko
Vertiefung öffnen

Warum indirekte Injection für RAG-Systeme das größere Risiko ist

Ein RAG-System, das Web-Inhalte, E-Mails oder hochgeladene Dokumente verarbeitet, kann nicht zuverlässig zwischen „Anweisung des Nutzers“ und „Text, der zufällig wie eine Anweisung aussieht, aber aus einem fremden Dokument stammt“ unterscheiden — sofern das System nicht explizit dafür gebaut wurde, diese Quellen zu trennen.

BegriffBedeutung
Direkte Prompt InjectionDer Angreifer gibt die manipulative Anweisung selbst direkt im Chat oder Prompt ein
Indirekte Prompt InjectionDie Anweisung ist in einem Dokument, einer Webseite oder E-Mail versteckt, die das System später im Rahmen von Retrieval oder Zusammenfassung verarbeitet
Merksatz

Jede Quelle, die ein RAG-System liest, ist ein potenzieller Angriffsvektor — nicht nur die direkte Chat-Eingabe.

02
RETRIEVAL POISONING

Wenn die vergiftete Quelle selbst ins Retrieval gelangt

Ein manipuliertes Dokument muss nicht einmal gezielt an eine Person gerichtet sein — es reicht, dass es in den Index gelangt.

Vertiefung öffnen

Der Angriffspfad

Gelangt ein präpariertes Dokument in eine Wissensbasis — etwa durch eine für alle beschreibbare geteilte Ablage, eine Webseite, die für Recherchezwecke abgerufen wird, oder eine eingereichte Bewerbungs- oder Support-Unterlage —, kann es beim nächsten passenden Retrieval automatisch abgerufen und in den Kontext des Modells eingespeist werden, ganz ohne dass ein Mensch das Dokument bewusst „ausgeführt“ hat.

Trainer-Frage

Welche eurer Wissensquellen sind für externe oder wenig kontrollierte Beiträge offen — und würden damit für Retrieval Poisoning in Frage kommen?

REALER FALL

Vertiefung öffnen
BEKANNTER FALL · WRITER.COM

Weißer Text auf weißem Grund steuerte die AI-Zusammenfassung und exfiltrierte private Daten

Im Dezember 2023 veröffentlichten Sicherheitsforscher (dokumentiert u. a. von Simon Willison und dem Team von PromptArmor) eine indirekte Prompt-Injection-Schwachstelle in der KI-gestützten Schreibplattform Writer.com. Der Angriff versteckte Anweisungen in „weißem Text auf weißem Hintergrund“ innerhalb einer Webseite. Wurde ein Nutzer dazu gebracht, diese Seite von Writer zusammenfassen zu lassen, aktivierten sich die versteckten Anweisungen: Das System wurde angewiesen, „die mittleren 50 Zeichen aller Quelldateien“ als Parameter an eine Bild-URL anzuhängen, wodurch beim Laden dieses Bildes private Dokumentinhalte über eine CloudFront-URL an den Angreifer abflossen. Writer wies die Schwachstelle zunächst zurück mit der Begründung, echte Kunden hätten keinen Website-Zugriff — eine Fehleinschätzung des tatsächlichen Risikos, das gerade in der Kombination aus Web-Zugriff und Zugriff auf private Unternehmensdaten liegt.

Bekannter Fall · öffentlich gemacht Dezember 2023
Warum das wichtig ist

Der Fall zeigt exemplarisch das Kernrisiko von RAG: Sobald ein System sowohl vertrauenswürdige, private Daten als auch nicht vertrauenswürdige, externe Inhalte verarbeiten kann, wird die externe Quelle zum Einfallstor für die private Quelle.

Trainer-Frage

Warum war „Kunden haben keinen Website-Zugriff“ als Gegenargument von Writer unzureichend?

04
EXFILTRATION

Wie gestohlene Daten das System tatsächlich verlassen

Der Writer.com-Fall nutzte eine Bild-URL — es gibt weitere gängige Exfiltrationsvektoren.

Vertiefung öffnen

Typische Vektoren

Markdown-Bilder oder Links mit codierten Daten in der URL (wie im Writer.com-Fall), automatisch ausgeführte Tool- oder Funktionsaufrufe mit vom Angreifer kontrollierten Parametern, sowie das Einbetten sensibler Daten in scheinbar harmlosen Fließtext, der später von einem weiteren System weiterverarbeitet wird. Allen gemeinsam: Der Datenabfluss geschieht über einen Kanal, der für legitime Funktionalität vorgesehen war und deshalb nicht standardmäßig blockiert wird.

Merksatz

Jeder Kanal, über den das System Inhalte nach außen rendern, aufrufen oder senden kann, ist ein potenzieller Exfiltrationsweg — nicht nur offensichtliche Uploads oder E-Mails.

05
GEGENMASSNAHMEN

DLP und Output Validation

Prävention muss auf zwei Ebenen ansetzen: was hineingelangt, und was herausgeht.

Vertiefung öffnen

Zwei ergänzende Kontrollschichten

Data Loss Prevention (DLP) erkennt und blockiert das Abfließen erkennbar sensibler Muster — etwa lange, unstrukturierte Zeichenketten in URL-Parametern, wie im Writer.com-Fall. Output Validation prüft generierte Antworten vor der Auslieferung auf verdächtige Strukturen, etwa automatisch geladene externe Bild- oder Link-URLs mit ungewöhnlich langen oder codierten Parametern, und blockiert oder entschärft diese, bevor sie im UI gerendert werden.

Trainer-Frage

Würde eure aktuelle Umgebung eine automatisch geladene Bild-URL mit 50 codierten Zeichen im Parameter erkennen oder blockieren?

06
CSP FÜR AI

Content-Security-Regeln für AI-Antworten

Was ein Browser für Webseiten längst tut, braucht eine AI-Oberfläche für generierte Antworten ebenso.

Vertiefung öffnen

Sandboxing-Prinzipien übertragen

Externe Bilder und Links in AI-generierten Antworten sollten nicht automatisch und ungeprüft geladen werden — analog zu einer Content Security Policy im Browser. Sinnvolle Regeln sind: keine automatische Anzeige extern gehosteter Bilder ohne Freigabe, Domain-Allowlists für eingebettete Links, und eine klare Trennung zwischen vom System vertrauenswürdig erzeugtem Text und aus Retrieval übernommenem Fremdinhalt in der Darstellung.

Merksatz

Sobald ein RAG-System Inhalte rendert, die technisch von außen beeinflussbar sind, gelten dieselben Sandboxing-Grundsätze wie im Web-Browser — nicht weniger.
